# v0.1.7 — The release tool finally admits which version it is

*Released 2026-08-31*

For its entire life, every copy of `git-release` has answered the question
"which version are you?" with a confident, cheerful `dev`. Not v0.1.6, not
v0.1.5 — `dev`. The published release artifacts said it. The binary on the
workstation said it. A tool whose entire job is keeping version numbers honest
had no idea what its own was.

The cause was three lines of Go that looked completely reasonable. The version
variables were initialised from another package's variables, which quietly
turns them into something the compiler has to set up at startup — after the
linker has already stamped the real value in. So the build stamped the tag, and
then the program's own first breath painted over it. Nobody noticed for five
months, because a binary that calls itself `dev` works perfectly well. It just
can't be identified, which turns out to matter enormously the moment you want
the same pinned version running in two places and want to *prove* it.

Fixed, and fixed in the way that stays fixed: the release pipeline now takes
the very binary it is about to publish, runs it, and refuses to ship if the
version it prints doesn't contain the tag being cut. The workflow also moved
back to a hosted runner — an earlier change had pointed it at a self-hosted
pool that is scoped to a different GitHub org and could never have picked up
the job, which nobody discovered because no tag was pushed after it landed.
This release is the first one in a while that actually had to run.
